# Автономный CD: каждый репозиторий деплоит себя

Staging деплоится из двух независимых источников: пуш в `main` API-репозитория (workflow `Deploy` стартует через `workflow_run` после успешного API CI) и запуск того же workflow со стороны UI-репозитория с `ui_sha` (вручную или по PAT из UI CI). Деплой обновляет только образ инициировавшей стороны, а версию другой стороны читает из текущего env-файла на VPS — поэтому каждому репозиторию достаточно собственных секретов и настроек, а общий `concurrency` выстраивает деплои в очередь. Исключение — первый деплой на свежем окружении без env-файла: ручной запуск с `ui_sha` берёт последний опубликованный API-образ целевой ветки.

Механизм одинаков для обоих окружений: `main` → staging (`/opt/dmc-268-t2`), `develop` → develop-окружение (`/opt/dmc-268-t2-develop`). Воркер деплоится вместе с API: API-образ — одна деплой-единица репозитория (один образ, два сервиса: `api` и `worker`).

## Considered Options

- Общий репозиторий-оркестратор — отклонено: лишний репозиторий и дублирование секретов ради перезапуска двух compose-сервисов.
- Mutable-тег `latest` для UI-образа, чтобы API-репо находил «последний» UI сам — отклонено: ломает принцип immutable `sha-`-тегов и воспроизводимость деплоя.
- `repository_dispatch` из UI-репозитория — отклонено: требует нового триггера и event-контракта при уже существующем `workflow_dispatch`; выигрыша перед ним нет.
