# Prompt Compression: AI Reviewer v4 → v5

**Задача:** [Issue #34 — Smart Summary, Risk Scoring и Prompt Compression](https://github.com/larchanka-training/dmc-268-ui-t2/issues/34)  
**Объём этого изменения:** только Prompt Compression; Smart Summary, Risk Scoring и автоматические метки PR здесь не реализуются.

## 1. Цель и подход

Подготовлена сокращённая версия системных инструкций и few-shot-примеров AI Reviewer. Новая версия **v5** основана на **v4** и использует прежние renderer, схемы и механизм исправления ответов. Целевое сокращение входных токенов — **20–30%**.

Оптимизированы повторяющиеся требования, служебные пояснения, длинные формулировки и текстовые части few-shot. Код PR, необходимый контекст, правила репозитория и структура результата не сокращались ради экономии.

| Компонент | Решение |
|---|---|
| Системные инструкции | Сокращены и объединены повторяющиеся формулировки |
| Few-shot | Сокращены текстовые пояснения; код, координаты, категории, severity и исправления сохранены |
| Renderer | Без изменений: `review-renderer-v4` |
| Provider / result schema | Без изменений: `llm-output/v2.json`, `review-result/v2.json` |
| Repair | Без изменений относительно v4 |
| Source context / AST, repository rules, Reflection | Требования v4 сохранены; их поведение на реальной модели пока не сравнивалось |
| Runtime defaults / staging | Не переключаются автоматически на v5 |

## 2. Примеры признанных избыточными формулировок

Ниже приведены характерные изменения. Полный текст — в `.agents/reviewer/v4/` и `.agents/reviewer/v5/`.

| Что сокращено | Было в v4 | Стало в v5 | Почему допустимо сократить |
|---|---|---|---|
| Описание роли | «Ты — ревьюер кода в сервисе AI Code Reviewer. Ты получаешь изменения одного pull request (один чанк) и возвращаешь только JSON по заданной схеме.» | «Ты — ревьюер кода AI Code Reviewer. Анализируй один чанк PR; верни только JSON по заданной схеме.» | Удалены лишние слова; роль, единица анализа и формат сохранены. |
| Допустимая severity | «Важность (`severity`), строго одна из: `critical`, `high`, `medium`, `low`. Значения `info` нет.» | «severity — одно из critical/high/medium/low; info запрещён.» | Сохранены те же допустимые значения и запрет `info`. |
| Выдуманные и повторные находки | «Не придумывай проблемы. Если замечаний нет, верни пустой список `findings`. Это нормальный результат.» и отдельный запрет дублирования | «Не выдумывай и не дублируй находки; без проблем findings=[].» | Два близких запрета объединены без удаления пустого результата. |
| `rule_ref` | Развёрнутое пояснение о метке нарушенного правила из `<repo_rules>`, примере `SEC-1` и `null` | «rule_ref (метка реально нарушенного переданного правила <repo_rules>, иначе null; метки не выдумывай)» | Сохранены происхождение метки, необходимость нарушения и `null` при отсутствии правила. |
| `evidence` | Отдельное определение конкретной строки/символа из diff и обоснования, плюс повтор в формате ответа | «evidence (обязательные конкретная строка/символ из diff и обоснование проблемы, не повтор title)» | Убран повтор списка полей; доказательство остаётся обязательным. |
| Координаты diff | Подробное повторное объяснение старой и новой стороны diff | Компактное требование к изменённой строке соответствующей стороны и включительному диапазону | Сохранены OLD/NEW, привязка к изменённой строке и запрет приблизительных координат. |
| Недоверенные данные и repository rules | Несколько разделов о `<pr_metadata>`, `<diff>`, `<repo_rules>`, `<source_context>`, командах в PR и приоритете системных правил | Объединённые инструкции о недоверенных данных, допустимых критериях репозитория и приоритете системных правил | Сохранены перечни источников, запрет следовать внедрённым командам и приоритет системных инструкций. |
| Примеры объяснений | «Если записи нет, `repo.get` возвращает `None`. Тогда `row.settings` бросает `AttributeError`…» | «Если repo.get вернёт None, row.settings вызовет AttributeError и ответ 500 вместо DEFAULTS.» | Сохранена цепочка причины и последствия; удалены вводные слова. |

**Ограничение:** текстовая проверка показывает сохранение перечисленных требований, но не доказывает, что реальная LLM будет одинаково точно находить дефекты, выбирать строки и сопротивляться prompt injection.

## 3. Методика расчёта

Использован штатный счётчик проекта `ConservativeTokenCounter`:

```text
estimated_tokens(text) = ceil(ceil(len(text.encode("utf-8")) / 3) × 1.15)
```

Дополнительно учитывались **4 служебных токена на сообщение**. Полный вход состоит из системных инструкций, выбранных few-shot сообщений, сериализованной схемы провайдера, пользовательского сообщения (метаданные, diff, repository rules, source context/AST) и framing. Это **консервативная оценка**, а не токены по токенизатору конкретной LLM, не `usage` провайдера и не фактическая стоимость.

Сравнивались шесть одинаковых входов: четыре небольших примера и два синтетических сценария с контекстом **80** и **387 строк**. Для обеих версий использованы одинаковые входные данные, правило репозитория и лимит входа 10 000 оценочных токенов. Сокращение входа по бюджету (`trimming`) не срабатывало; код, схемы, контекст и выбранные few-shot ID не менялись.

### Суммарный результат на шести входах

| Компонент, оценочных токенов | v4 | Оптимизированная версия | Экономия |
|---|---:|---:|---:|
| Системные инструкции | 14 202 | 9 414 | 4 788 |
| Выбранные few-shot | 4 039 | 3 606 | 433 |
| Provider schema | 4 062 | 4 062 | 0 |
| Метаданные, diff, правила, source context/AST | 8 328 | 8 328 | 0 |
| Framing | 144 | 144 | 0 |
| **Полный вход** | **30 775** | **25 554** | **5 221** |

**Итоговая расчётная экономия: 5 221 / 30 775 = 16,97%.** Системный текст на одно сообщение уменьшился с **2 367 до 1 569** оценочных токенов (**−33,71%**).

### Результат по каждому входу

| Пример | v4 | Оптимизированная версия | Экономия |
|---|---:|---:|---:|
| contract-context | 3 999 | 3 132 | 21,68% |
| python-unhandled-none | 3 952 | 3 085 | 21,94% |
| typescript-sql-injection | 3 955 | 3 069 | 22,40% |
| no-findings | 3 954 | 3 087 | 21,93% |
| Синтетический source context, 80 строк | 5 253 | 4 386 | 16,50% |
| Синтетический source context, 387 строк | 9 662 | 8 795 | 8,97% |

Экономия составляет примерно **867–886 оценочных токенов на запрос**. Поэтому на больших PR её относительная величина ниже: полезный код и контекст остаются неизменными. **Ориентир 20–30% не достигнут для суммарного набора из шести входов**, и дальнейшее сокращение не должно устранять необходимые требования безопасности и качества.

## 4. Проверки, ограничения и дальнейшее решение

Выполнены три минимальные проверки (`3 passed`): загрузка и проверка digest, совместимость с renderer/schema v4, сохранение пользовательского контекста и правил, а также выбор версии в тестовой конфигурации. Расчёт запускался дважды с побайтово одинаковым JSON-результатом.

**Новый bundle digest для версии v5** (при исходных хешах трёх файлов и `review-renderer-v4`):

```text
d0dc1f41a4b78930997fff2e43c338187d1756530a1b31ef1f03172f4214d050
```

Фактическое качество ревью **не проверялось**: реальных LLM-вызовов, A/B-сравнения обнаруженных дефектов и измерения provider token usage не было. Полный тестовый набор и интеграционные проверки для этого этапа не запускались. Решение о live-проверке, модели, бюджете и включении v5 в runtime предлагается согласовать с командой отдельно.

**Вывод:** новая версия даёт подтверждённое *по методике проекта* сокращение оценочного размера входа на выбранных примерах при сохранении исходного кода и контекста. Это **кандидат для обсуждения и последующего испытания**, а не доказательство неизменного качества LLM или готовности к production.
