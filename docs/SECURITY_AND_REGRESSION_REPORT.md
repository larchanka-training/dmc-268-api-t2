# Отчёт: регрессионное тестирование, chaos-сьют и security-аудит

Задача: граничные и аварийные сценарии (таймаут LLM API, 429, падение воркера, сетевые сбои GitHub), регрессионные испытания цикла ревью, security-испытания (подмена правил, инъекции в заголовках коммитов, изоляция секретов в логах).

## 1. Методика

- **Носитель сбоев — фейки на публичных швах** (LLM gateway, transport, attempt store, публикация) при реальных PostgreSQL и Redis: детерминированно, без внешних сервисов, повторяемо в CI.
- Существующее покрытие сохранено и переиспользовано (gateway, PEL/lease/outbox recovery, reconcile); chaos-сьют дополняет его **сквозными сценариями**, которых не было.
- Security-испытания — через продакшн-пайплайн (вебхук-захват → frozen configuration → рендер промпта → LLM → детерминированная валидация) и через реальный конвейер логирования (structlog → stdlib root → файл, JSON).
- Прогон: `uv run pytest -m chaos` (8 сценариев) и полный сьют `uv run pytest -m "not chaos"` (2042 passed; 11 падений — заранее воспроизведены на чистом `main`, средовые: docker/deploy-скрипты, к данной задаче не относятся).

### Наблюдения вне скоупа (не чинилось)

1. **`reconcile()` публикаций недостижим из production-кода.** `PostgresTaskLeaseStore.acquire` выдаёт publish-лизу только для `PENDING`-публикаций, а `check_reconciliation_authority` требует живой лизы со строгим бóльшим fencing-токеном. После парковки `UNKNOWN` лиза освобождается — ни один продакшн-путь не может получить полномочия на reconcile; разрешение требует ручного SQL. Тикет: #52.
2. **Побочный мутатор глобальных уровней логгеров.** Цикл `publication_worker.run` поднимает уровень `httpx`/`httpcore` до WARNING на весь процесс. Для выделенного процесса воркера — норма, но любой in-process запуск (тесты, инструменты) молча теряет transport-логи. Зафиксировано как источник хрупкости тестового контекста.

## 3. Регрессия цикла ревью

**Факт:** механизма межцикловой дедупликации в коде сегодня нет: каждый push — новый цикл, полный diff от merge-base, новое ревью на захваченный head. Дедупликация по fingerprint действует внутри цикла, идемпотентность повторной доставки — по маркеру `<!-- dmc268-review:v1 review=… head=… -->`, привязанному к review_id.

**Граница поставки.** Требование спринта 4 — после нового коммита не дублировать замечания к неизменённым строкам (#51, направление UI dmc-268-ui-t2#28 и backend dmc-268-ui-t2#33) — этим PR не закрывается и изменение требований не фиксирует: межцикловой повтор замечания — текущее ограничение реализации. Этот PR закрывает только цикловые гарантии; инкрементальная приёмка остаётся открытой — тикет #53.

Закреплено тестом `tests/test_review_cycle_regression.py`:

- повторная доставка завершённого цикла возвращает сохранённый исход и не делает ни одной записи в GitHub;
- новый цикл публикует собственное ревью, привязанное к захваченному head (`commit_id` в запросе); цикл 2 в тесте — реальный новый коммит: PR head сдвигается на новый SHA и на стороне снапшота, и на стороне GitHub-фейка;
- старое ревью не редактируется и не дополняется;
- повтор того же замечания на неизменённой строке в новом цикле публикуется — текущее ограничение, зафиксированное тестом as-is; подавление — открытая приёмка #53.

### Тикет #53 (создан)

**Заголовок:** Межцикловые повторы замечаний: возможное подавление повторов по fingerprint (#53).

**Проблема.** Новый цикл ревью публикует новое ревью на новый head; замечание на неизменённой строке LLM может переотчитать, и в таймлайне PR появятся дубликаты одного замечания из разных циклов. Дедупликация по fingerprint действует только внутри цикла; маркер публикации содержит `review_id`, поэтому cross-cycle подавление сейчас невозможно.

**Варианты.**
1. Не менять (status quo): боты-ревьюеры так и работают; старые комментарии остаются на своих коммитах.
2. Подавление при подготовке: перед публикацией сверять fingerprint'и нового цикла с комментариями предыдущих циклов на PR (по `dmc268-finding:` маркерам) и исключать повторы (в корпус ревью — «уже отмечено»).
3. Подавление на стороне LLM: передавать существующие замечания в контекст (растёт стоимость и риск инъекций через комментарии).

**Оценка.** Вариант 2 — локальная правка `prepare_github_review` + сверка через `_comment_references`; требует решения о «правде» при расхождении (строка изменилась между циклами).

## 4. Security

### 4.1 Подмена правил (`.review/rules.md`, эксплойты)

- VCS-загрузчика `.review/rules.md` в системе сегодня нет (ADR-0002, будущий #23): правила — canonical-документ в БД с digest-freezing (тройная проверка digest при исполнении). Вектор «автор PR подменяет rules.md в своём diff» к текущему коду неприменим.
- Промпт v1 **отказывается исполняться** с непустыми правилами (`v1 cannot render repository instructions`); v2/v3 рендерят правила изолированным блоком с нейтрализацией делимитеров.
- End-to-end с hostile-корпусом (`</repo_rules>`, `<|im_start|>system`, `</repository_instructions>`, «игнорируй все правила») — `tests/test_security_prompt_injection_e2e.py`: все инъекции остаются данными внутри забора, структурный забор не взламывается, системное сообщение не загрязняется.

**Находка F-1 (ticketed, low).** Рендерер v2 нейтрализует только 4 из 6 защищённых тегов: сырые `</repo_rules>`/`<repo_rules>` проходят в блок правил как текст. Сегодня это инертно (правила рендерятся JSON-строкой внутри `<repository_instructions>`, структурный забор не открывается/не закрывается), но фикс требует изменения рендерера → пересчёт sha256 в `manifest.json` (изменение идентичности frozen-бандла). Решение — команде, вместе с admittance-переключением на v3.

### 4.2 Инъекции в заголовках коммитов и PR

- Title/body попадают в промпт только как данные внутри `<pr_metadata>` с нейтрализацией делимитеров и лимитами (триминг до 1000 символов, ≤20 коммитов). Уровни проверки разделены: hostile title/body прогнаны сквозным тестом через production-пайплайн (GitHub-фейк); commit-сообщения покрыты только юнит-тестами рендерера — сквозной сценарий с ними сегодня неприменим, production GithubClient захватывает metadata с `commit_messages=[]` (`src/app/vcs/github.py`), заголовки коммитов в снапшот не попадают.
- Ответ LLM, пытающийся пронести поля вне провайдерской схемы (`rule_ref` в v1/v2-проводке), отбраковывается целиком: обе попытки → `invalid_llm_output` → терминальный `FAILED` без находок и публикации (`test_llm_cannot_smuggle_schema_fields_past_validation`).

### 4.3 Изоляция секретов в логах

Тесты `tests/test_security_secrets_in_logs.py` прогоняют реальный конвейер логирования (structlog → stdlib root → файл, JSON) и сканируют каждую запись на каждое сконфигурированное значение секрета (webhook secret, GitHub write-токен, ключ LLM, JWT-секрет):

- попытка log-injection через `X-Request-Id` (секрет + `\r\n`) нейтрализуется middleware: ид валидируется, чужой ид не переиспользуется, вторая строка в лог не попадает;
- HMAC-подписи и секреты не появляются в записях ни на одном уровне, включая DEBUG;
- invalid-signature запрос возвращает безопасную ошибку без эха payload'а;
- gateway-события (`llm_attempt_*`) не содержат API-ключей и Authorization-заголовков.

**Утечек не найдено.** Существенную роль играет уже имевшаяся защита: `SecretStr` во всех секретах конфига, агрессивный scrubbing в Sentry, коды ошибок вместо тел ответов провайдера.

## 6. Протокол ручного SIGKILL-эксперимента (выполнение — вне этой задачи)

Цель: подтвердить на живом окружении то, что chaos-сьют доказывает на швах, — восстановление после смерти процесса воркера посреди обработки.

Подготовка: окружение из `docker-compose.staging.yml` (api + worker + webhook-worker + Postgres + Redis), доступ к БД и Redis окружения.

1. Довести PR до состояния «анализ в процессе»: открыть PR с изменениями, дождаться появления задачи анализа (`select status, started_at from review_job order by created_at desc limit 1;` → `status = 'ANALYSIS'`/аналогичный активный).
2. Убедиться, что LLM-вызов в полёте: `select state from review_llm_attempt order by reserved_at desc limit 1;` → `RESERVED` (или журнал воркера показывает исходящий вызов).
3. Убить воркера посреди вызова: `docker kill $(docker compose -f docker-compose.staging.yml ps -q worker)`.
4. Наблюдать: контейнер перезапускается (restart policy); в течение `min_idle_time` (90 c) + интервала recovery доставка возвращается из PEL: `redis-cli XPENDING dmc268:review-tasks:analyze review-workers`.
5. Критерии успеха:
   - задача доводится до терминального состояния без ручного вмешательства (`review_job.status ∈ {COMPLETED, PARTIAL, FAILED}` и `finished_at is not null`);
   - в PR появляется **не более одного** ревью-комментария на это событие (без дублей);
   - `review_llm_attempt` показывает прерванную попытку (`RESERVED`/`ERROR`) и следующую с большим fencing-токеном;
   - публикация либо `PUBLISHED`, либо безопасный `UNKNOWN`/`FAILED` с подтверждённым отсутствием записей — но никогда не дублируется.
6. Зафиксировать в этом отчёте фактические времена восстановления и наблюдения (создать PR-комментарий к протоколу).
